# **Краткие теоретические сведения**

## **Пользователи и группы**

Linux — многопользовательская система: каждый процесс и каждый файл принадлежат какому-либо пользователю. Для ядра пользователь идентифицируется особым числом  UID (user id). Символьные имена удобны для пользователей. UID суперпользователя root равен 0, он обходит большинство проверок прав. В Debian обычные пользователи получают UID начиная с 1000, а меньшие номера заняты системными учётными записями служб (www-data, sshd и др.), под которыми работают системные службы без права интерактивного входа.

Данные об учётных записях лежат в текстовых файлах. В /etc/passwd хранятся имя, UID, GID основной группы, домашний каталог и шелл (поля через двоеточие). В /etc/group — группы и их члены. В /etc/shadow — хеши паролей и сроки их действия; читать его может только root. Хеш в shadow включает случайную «соль», поэтому одинаковые пароли дают разные записи. Удобно читать эти базы командой getent, а не cat, потому что getent учитывает и другие источники учётных записей.

У пользователя есть одна основная группа и сколько угодно дополнительных. Основная группа назначается новым файлам пользователя, дополнительные дают доступ к общим ресурсам. Управление: adduser и userdel (создание и удаление), usermod (изменение, в частности usermod \-aG группа пользователь добавляет в дополнительную группу), groupadd, groupdel, groupmod, passwd (смена пароля), chpasswd (массовая смена паролей из stdin). Команда id показывает UID, GID и все группы, groups — только группы. Изменения в группах применяются к новым сессиям, уже запущенные сессии их не видят.

## **Права на файлы и каталоги**

К каждому файлу применяются три тройки прав: для владельца (user), для группы, которая владеет файлом (group) и права для остальных (other). В каждой тройке три бита: r (чтение), w (запись), x (выполнение). Просматривать права можно через ls \-l, менять — chmod, менять владельца и группу — chown и chgrp. Права удобно записывать в восьмеричном виде: r \= 4, w \= 2, x \= 1, поэтому rwxr-x--- — это 750\. Права, которые получает новый файл, определяются маской umask, вычитающей биты из 666 (файлы) или 777 (каталоги).

Для файла r разрешает читать содержимое, w — изменять его, x — запускать как программу. Для каталога смысл иной. r позволяет получить список имён (ls), x — «проходить» через каталог: заходить в него (cd) и обращаться к файлам по имени, в том числе читать их атрибуты. w позволяет создавать, переименовывать и удалять записи в каталоге, но работает только вместе с x. Важно: удалить файл можно, имея w на каталог, даже если на сам файл прав нет. Каталог без x практически недоступен, даже если на нём есть r.

Кроме трёх основных пар есть специальные биты. suid (4000) на исполняемом файле запускает программу с правами её владельца, а не запустившего (так работает passwd, которому нужно писать в shadow). sgid (2000) на файле запускает с правами группы-владельца, а на каталоге заставляет новые файлы наследовать группу каталога. sticky bit (1000) на каталоге разрешает удалять и переименовывать файлы только их владельцу, владельцу каталога и root (так устроен /tmp). Выставленные биты видны в ls \-l: s на месте x (или S, если x нет) и t в конце. Файл с suid и владельцем root — потенциально опасный объект: ошибка в такой программе даёт злоумышленнику права root.

Помимо классической модели существуют списки ACL (setfacl, getfacl), которые позволяют выдать права конкретному пользователю или группе без смены владельца. В этой работе они не используются на практике, только в одном вопросе отчёта.

## **SSH: подключение по паролю и по ключам**

SSH (Secure Shell) создаёт шифрованный канал между клиентом и сервером. Серверная часть — служба sshd из пакета openssh-server, в Debian её юнит называется ssh (имя sshd работает как псевдоним), слушает TCP-порт 22\. Настройки лежат в /etc/ssh/sshd\_config, а также в файлах каталога /etc/ssh/sshd\_config.d/. Для большинства параметров действует первое найденное значение, поэтому настройка в основном файле может не сработать, если тот же параметр задан раньше во вложенном файле. Узнать значения, которые сервер реально использует, можно командой sshd \-T (нужны права root). Перед перезапуском службы проверяйте синтаксис командой sshd \-t.

При первом подключении клиент показывает отпечаток открытого ключа сервера и просит подтвердить доверие; принятый ключ записывается в \~/.ssh/known\_hosts. Если ключ сервера изменится, клиент поднимет тревогу — это защита от подмены сервера. Аутентификация пользователя возможна по паролю или по ключу. Ключ — это пара файлов, созданная ssh-keygen: закрытый (остаётся у вас, например id\_ed25519) и открытый (.pub, его копируют на сервер в файл \~/.ssh/authorized\_keys пользователя). Закрытый ключ можно защитить парольной фразой. Для копирования файлов по SSH служит scp.

Параметры sshd, важные для безопасности: PermitRootLogin (разрешён ли вход root; значение по умолчанию в Debian — prohibit-password, то есть только по ключу), PasswordAuthentication и PubkeyAuthentication (допустимые способы входа), MaxAuthTries (число попыток аутентификации за соединение), LoginGraceTime (время, отведённое на завершение входа; по истечении неавторизованное соединение закрывается), Port. После изменения конфигурации службу перезапускают командой systemctl restart ssh или перечитывают конфигурацию командой systemctl reload ssh. Ошибка в настройках может закрыть вам доступ на сервер, поэтому всегда держите открытой вторую рабочую сессию, пока не проверите новый вход.

## **Повышение привилегий: su и sudo**

Команда su позволяет переключиться на другого пользователя (по умолчанию root), но требует пароль целевого пользователя. su \- (с дефисом) запускает полноценный вход с окружением целевого пользователя, а su без дефиса сохраняет значительную часть окружения текущего. Команда sudo выполняет одну команду с правами другого пользователя (по умолчанию root) и запрашивает пароль вызвавшего, а не целевого. Это удобнее и безопаснее: пароль root не раздаётся, а каждое использование записывается в журнал. В Debian право пользоваться sudo даёт членство в группе sudo (пакет sudo нужно поставить, если при установке был задан пароль root).

Тонкая настройка выполняется в /etc/sudoers и в файлах каталога /etc/sudoers.d/. Правило имеет вид «кто где\=(от\_имени\_кого) команды», например: user1 ALL=(root) /usr/bin/passwd. Файлы sudoers нельзя править обычным редактором: ошибка синтаксиса блокирует sudo целиком. Используйте visudo (visudo \-f /etc/sudoers.d/имя), он проверяет синтаксис при сохранении, а файлы в sudoers.d должны иметь права 0440\. Команда sudo \-l показывает, что вам разрешено.

## **Процессы**

Процесс — это экземпляр запущенной программы. Каждый процесс имеет идентификатор PID и идентификатор родителя PPID: новые процессы создаются вызовом fork родителем, а затем, как правило, заменяют образ программы вызовом exec. Все процессы выстроены в виде дерева. Корнем дерева процессов является процесс с PID 1 (systemd), от него происходят все остальные. Когда родитель завершается раньше потомка, потомка «усыновляет» системный процесс. Процесс, который завершился, но родитель ещё не прочитал его код возврата, называется зомби (состояние Z).

Посмотреть процессы можно командами ps (например, ps \-ef или ps \-eo pid,ppid,user,stat,cmd), pstree \-p (дерево с PID) и интерактивной утилитой htop (может отсутствовать в системе и ставится через apt). В htop доступны сортировка по столбцам (F6), древовидный режим (F5), фильтр (F4), поиск (F3) и отправка сигнала выбранному процессу (F9). Состояния процесса в столбце S/STAT: R — выполняется, S — спит и ждёт события, D — ожидает ввода-вывода, T — остановлен, Z — зомби.

Управление процессом выполняется сигналами. Команда kill PID посылает по умолчанию сигнал SIGTERM (15), просьбу завершиться, которую процесс может обработать и корректно закрыть файлы. Сигнал SIGKILL (9) убивает процесс принудительно и не может быть перехвачен. SIGSTOP и SIGCONT останавливают и возобновляют выполнение, SIGHUP посылается процессам при закрытии управляющего терминала и по умолчанию их завершает. Команды pkill и killall находят процесс по имени. Сигнал можно отправить только своему процессу, а чужому — только от имени root.

## **Фоновый запуск процессов**

Команда, запущенная в терминале, занимает его до завершения. Добавление & в конец строки запускает её в фоне, при этом оболочка выводит номер задания и PID, а PID последнего фонового процесса доступен в переменной \$\!. Нажатие Ctrl+Z останавливает текущую задачу, bg продолжает её в фоне, fg возвращает на передний план, jobs перечисляет задания текущей оболочки. Эти механизмы относятся к одной оболочке: при её закрытии процессы получают SIGHUP и завершаются.

Чтобы процесс пережил закрытие терминала или обрыв SSH-соединения, его запускают через nohup команда & (nohup игнорирует SIGHUP и по умолчанию пишет вывод в файл nohup.out), либо отсоединяют от оболочки командой disown, либо запускают в новой сессии через setsid. Для долгоживущих служб в современных системах используются юниты systemd, для интерактивной работы — мультиплексоры tmux и screen; в этой работе они не рассматриваются.

### **Часть 6\. Аудит безопасности в скрипте инвентаризации**

В Практических работах №1 и №2 вы создали скрипт, собирающий отчёт о системе по этапам: сбор сырых данных, обработка, логирование. Скопируйте script\_passport\_v2.sh в script\_passport\_v3.sh и расширьте его. Сохраните архитектурное разделение на этапы и не переписывайте скрипт с нуля.

В этой части вам нужно выполнить рефакторинг кода, оформив повторяющиеся фрагменты как функции и добавить в отчет (PASSPORT/inventory.txt) разделы по безопасности.

Доработайте скипт, так, чтобы осуществлялись: 

1\. Проверка достаточности прав. Функция check\_privileges должна определить, запущен ли скрипт от root или пользователем из группы sudo (с рабочим sudo), и при отсутствии прав сообщить об этом и завершить скрипт с ненулевым кодом. Запускаемые под sudo команды должны вызываться только при необходимости.

2\. Оформление фрагментов в виде функций. Минимальный набор: check\_privileges (права), check\_tool (наличие нужной утилиты; сообщает, какой пакет установить), write\_section (заголовок раздела и вывод его содержимого в итоговый файл), log\_run (запись строки о запуске в лог с датой, причем необходимо расширить лог, указывая версию формата файла репорта – v3), usage (справка при \-h). Дополнительно \- die (сообщение об ошибке в stderr и выход с кодом) и cleanup (удаление временных файлов). Имя итогового файла отчёта должно приниматься параметром, а по умолчанию использоваться PASSPORT/inventory.txt.

3\. Добавление в отчет раздела «Пользователи». Для каждой обычной учётной записи (UID ≥ 1000\) и root выведите: имя, UID, список групп, время последнего входа и дату последней смены пароля. Рекомендуемые источники: getent passwd, id \-nG, chage \-l, lastlog2 (или lslogins — сравните их).

4\. Добавление в отчет раздела «Параметры sshd». Выведите эффективные значения: разрешён ли вход root (permitrootlogin), порт (port), время на вход (logingracetime), а также maxauthtries, passwordauthentication и pubkeyauthentication. Источник — sshd \-T. Дополнительно покажите, какие из этих параметров явно прописаны в конфигурации, а какие взяты по умолчанию (см. вопрос в отчёте).

5\. Добавление в отчет раздела «Топ-5 процессов». Пять процессов с наибольшим потреблением памяти (PID, PPID, пользователь, %MEM, команда). Источник — ps с сортировкой.

6\. Добавление в отчет раздела «Подозрительные учётные записи»: пользователи с пустым паролем в /etc/shadow и пользователи с UID 0, кроме root.

7\. Добавление в отчет раздела «Файлы с suid»: список файлов с suid в /usr/bin и /usr/sbin.

**Примечания:**

* *В Debian 13 команды lastlog из коробки больше нет - она удалены из пакетов util-linux и login. Нужно установить пакет lastlog2 (замена lastlog). После установки надо перегрузить систему иначе данных о ваших входах не будет. Скрипт обязан корректно сообщать «нет данных», если утилиты нет или записей нет, а не завершаться ошибкой.*  
* Вывод chage \-l зависит от языка системы. Для разбора запускайте её с LC\_ALL=C, а нужные поля вытаскивайте через grep, sed или awk, а не по номеру строки.*

* *Добавляйте новые временные файлы и новые секции по той же схеме, что и в ПР №1 и ПР №2: сбор сырых данных во временные файлы, формирование отчёта, запись строки в лог. Удаление временных файлов делайте в функции cleanup.*
